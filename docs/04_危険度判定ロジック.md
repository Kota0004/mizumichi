# 04. 危険度判定ロジック

作成日: 2026-08-19

このドキュメントは本アプリの中核である **「降水量から、その地点が危険かどうかを決める計算」** を定義する。

---

## 0. 設計方針

> **全国一律の「○mm以上で危険」は使わない。地点ごとに閾値を持たせ、雨量をその閾値で正規化する。**

理由は [01](01_背景と課題整理.md) の第4節。同じ50mm/hでも高台では何も起きず、アンダーパスでは車が水没する。
したがって計算の骨格は

```
危険度 = f( その地点の雨量 ÷ その地点の冠水閾値 ,  先行降雨 ,  キキクル ,  実測・目撃情報 )
```

とし、**「閾値」を地点属性として持つ**。ユーザーの言う「降水量でフィルタを掛ける」は、
この式の雨量に任意の値を代入する操作（`what-if` モード）として自然に実装できる。

---

## 1. 用語と入力

### 1-1. 地点（Spot）の属性

| 記号 | 名称 | 型 | 取得元 |
|------|------|----|-------|
| `type` | 種別 | enum: `underpass_pump` / `underpass_gravity` / `lowland` / `river_adjacent` / `bridge_approach` | 公的マップ、OSM、DEM解析 |
| `T60` | **時間雨量の冠水閾値** (mm/h) | float | 既定値＋履歴学習（1-3節） |
| `Tburst` | **短時間強雨の閾値** (mm/h換算) | float | 既定 `T60 × 1.4` |
| `dz` | 周辺100mとの相対標高 (m) | float | 国土地理院 標高タイル |
| `hist` | 過去の冠水確認回数 | int | 公的資料＋アプリ内報告の蓄積 |
| `conf` | データ信頼度 | 0–1 | 公的=1.0 / 機械抽出=0.5 / 投稿のみ=0.3 |

### 1-2. 時刻 t における観測・予測

| 記号 | 内容 | 出典 | 更新 |
|------|------|------|------|
| `R10` | 直近10分間の降水量 (mm) | アメダス（IDW内挿）／ナウキャスト | 10分 / 5分 |
| `R60` | 直近60分間の降水量 (mm) | 同上 | 10分 |
| `R180` | 直近3時間の累積降水量 (mm) | 同上 | 10分 |
| `F30` | 今後30分の予測降水量 (mm) | 高解像度降水ナウキャスト | 5分 |
| `K` | 浸水キキクル レベル（0=なし … 4=災害切迫） | 気象庁 | 10分 |
| `U` | ユーザー報告スコア（1-5節） | 自前 | 随時 |
| `O` | 公的な通行止め・冠水確定（0 or 1） | 自治体／千葉市地下道システム | 随時 |

## 2. 面的な雨量の作り方（点観測から地点値へ）

無料で数値が取れるのはアメダス（点）だけなので、次の2段構えで地点値を作る。

```
1) ナウキャストのPNGタイルを読み、地点のピクセル色 → 凡例テーブル → 雨量強度 I_tile [mm/h]
2) 近傍アメダス3点を距離の逆二乗で重み付け（IDW） → I_amedas [mm/h]
3) R10 ≒ (0.7 * I_tile + 0.3 * I_amedas) / 6      # 10分値に換算
   ※ タイル取得に失敗したら I_amedas のみで代替（劣化動作）
```

- 凡例テーブルは `{RGB → 階級の代表値}` の対応表として持ち、**設定ファイルに外出し**する（気象庁側の凡例変更に備える）。
- タイルは `z=10`（≒ 100m/px 級）で取得し、地点の緯度経度からピクセル座標を求める。

```python
# 緯度経度 → タイル座標 + ピクセル座標（Web メルカトル）
def lonlat_to_pixel(lon, lat, z):
    n = 2 ** z
    x = (lon + 180.0) / 360.0 * n
    lat_rad = math.radians(lat)
    y = (1.0 - math.asinh(math.tan(lat_rad)) / math.pi) / 2.0 * n
    tx, ty = int(x), int(y)
    px, py = int((x - tx) * 256), int((y - ty) * 256)
    return tx, ty, px, py
```

## 3. 地点閾値 `T60` の決め方

### 3-1. 既定値（データがない地点の初期値）

| `type` | 既定 `T60` (mm/h) | 根拠 |
|--------|------------------|------|
| `underpass_gravity`（自然排水のアンダーパス） | **35** | 排水能力が低く最も危険。下水道の計画降雨50mmを下回る段階で溜まりうる |
| `underpass_pump`（ポンプ付きアンダーパス） | **55** | 市街地下水道の計画排水能力 50mm/h 相当＋ポンプ余力 |
| `lowland`（窪地・低地） | **50** | 内水氾濫の一般的な目安 |
| `bridge_approach` | **60** | |
| `river_adjacent` | — | 雨量ではなく**河川水位**で判定（4-4節） |

### 3-2. 地形による補正

標高タイルから求めた相対標高 `dz`（周辺100m平均との差、単位m）で補正する。

```
T60 ← T60 × clamp(1 + 0.12 × dz, 0.6, 1.4)
```
`dz = -2m`（2m窪んでいる）なら係数0.76 → 閾値が下がり、危険と判定されやすくなる。

### 3-3. 履歴による補正

```
T60 ← T60 × (1 - 0.05 × min(hist, 5))     # 最大25%引き下げ
```

### 3-4. 学習（フェーズ2以降）

投稿・センサーで「冠水した／しなかった」のラベルが溜まったら、地点ごとに

```
P(冠水) = σ( a·R60 + b·R180 + c )
```

のロジスティック回帰を当て、`P = 0.5` となる `R60` を新しい `T60` とする。
サンプルが少ない地点は、**同じ `type` の全国事前分布に縮小推定（shrinkage）**して暴走を防ぐ。

## 4. 危険度スコアの計算

### 4-1. 雨量の超過度

```
R60_eff = max( R60 ,  R60 + F30 )          # 30分先まで見込む（予測モード時）
I_rain  = max( R60_eff / T60 ,  (R10 × 6) / Tburst )
```

### 4-2. 先行降雨（地面と下水の余力低下）

```
A = 1 + min(0.30, R180 / 300)               # 3時間で300mm降っていれば +30%
I_rain ← I_rain × A
```

### 4-3. 合成スコア（0–100）

```
S = 100 × clamp(
      0.60 × clamp(I_rain, 0, 2) / 2
    + 0.25 × (K / 4)
    + 0.15 × min(hist, 5) / 5
    , 0, 1)
```

- 雨量が支配的（60%）。キキクル（25%）で面の状況を、履歴（15%）で場所の弱さを反映。
- `I_rain = 1`（＝ちょうど閾値）で `S ≈ 30 + キキクル寄与`。**閾値ちょうどでレベル2（警戒）に入る**ように係数を置いている。

### 4-4. 河川隣接地点（`river_adjacent`）の別ロジック

雨量ではなく水位で判定する。水位観測所の**氾濫注意水位／避難判断水位に対する比**を `I_rain` の代わりに使う。
無料での数値取得手段が限られるため（→02のR7）、**MVPでは洪水キキクルのレベルで代用**する。

### 4-5. 実測・確定情報によるオーバーライド

計算値より**現地の事実が常に優先**する。

```
if O == 1:                          level = 4   # 公的な通行止め・冠水確定
elif U >= 0.8:                      level = 4   # 高信頼の目撃報告（膝上／複数一致）
elif U >= 0.5:                      level = max(level, 3)
else:                               level = level_from(S)
```

### 4-6. レベル定義

| Lv | 名称 | S の目安 | 色 | 通知 | 文言（例） |
|----|------|---------|----|------|-----------|
| 0 | 平常 | 0–14 | 灰 | なし | — |
| 1 | 注意 | 15–34 | 黄 | なし（地図のみ） | 「雨が強まれば冠水する可能性のある場所です」 |
| 2 | 警戒 | 35–59 | 橙 | 接近時のみ | 「500m先アンダーパス。冠水しやすい場所です。速度を落としてください」 |
| 3 | 危険 | 60–79 | 赤 | 接近＋エリア | 「冠水の可能性が高い場所です。迂回を検討してください」 |
| 4 | 極めて危険（報告由来の場合は「通行不能情報」） | 80–100 またはオーバーライド | 紫 | 即時 | 計算由来:「冠水により通行できない可能性が高い状況です。進入しないでください」<br>報告・公的情報由来:「冠水の報告があります。進入しないでください」 |

> 色だけでなく**形（アイコン）と文言**でもレベルを区別する（色覚多様性への配慮）。

## 5. ユーザー報告スコア `U`

```
U = clamp( Σ_i ( w_depth(i) × w_photo(i) × w_user(i) × decay(Δt_i) ) , 0, 1 )
```

| 係数 | 値 |
|------|----|
| `w_depth` | くるぶし=0.3 / 膝=0.7 / 膝上・車が水没=1.0 |
| `w_photo` | 写真あり=1.0 / なし=0.6 |
| `w_user` | 過去の投稿が追認された率に応じて 0.5–1.2（新規は0.8） |
| `decay(Δt)` | `exp(-Δt / 90分)`。**3時間で自動失効** |
| 反証 | 「もう引いた」報告は `U` から減算（同じ重み体系） |

**投稿がGPS実測位置と500m以上離れている場合は採用しない**（いたずら・遠隔投稿の抑止）。

## 6. 誤報を減らす仕組み

冠水アプリの最大の失敗は「**オオカミ少年になって無視されること**」。次を必ず入れる。

| 仕組み | 内容 |
|-------|------|
| **ヒステリシス** | レベルを上げる閾値と下げる閾値を分ける（上げ: S≥60、下げ: S<52）。境界での点滅を防ぐ。 |
| **クールダウン** | 同一地点の通知は**60分に1回**まで。 |
| **進行方向判定** | 現在地から見て**進行方位±60度**の範囲にある地点のみ走行中通知（→ F-21）。 |
| **通知予算** | 1イベント（豪雨）あたりの通知は最大N件。優先度の高いものだけ残す。 |
| **レベル1は通知しない** | 地図で見えるだけにする。 |
| **事後フィードバック** | 通知後に「実際どうでしたか？（冠水していた／していなかった）」を1タップで回収し、`T60` の学習に回す。 |

## 7. 「降水量フィルタ」の実装（ユーザー要望の直接の答え）

UIのスライダーで `R60` に任意の値を代入し、`F30 = 0`, `R180 = R60 × 1.5`, `K = 推定値` として再計算する。

```
onSliderChange(rain_mm_per_h):
    for spot in visible_spots:
        S = score(spot, R60=rain_mm_per_h, R10=rain_mm_per_h/6, R180=rain_mm_per_h*1.5, F30=0, K=estimate(rain_mm_per_h))
        spot.level = level_from(S)
    redraw()
```

`K` の推定は簡易に `rain→キキクル階級` の対応表で行う（30mm/h→1, 50→2, 80→3, 100+→4）。

### 計算例（自然排水のアンダーパス、`dz = -1.8m`、`hist = 3`）

```
T60 = 35 × (1 + 0.12×(-1.8)) × (1 - 0.05×3)
    = 35 × 0.784 × 0.85 ≈ 23.3 mm/h
```

| スライダー | `I_rain`（A込み） | `K` | `S` | レベル |
|-----------|------------------|-----|-----|-------|
| 20 mm/h | 20/23.3 × 1.10 = 0.94 | 0 | 0.60×0.47×100 + 0 + 9 = **37** | 2 警戒 |
| 30 mm/h | 30/23.3 × 1.15 = 1.48 | 1 | 44.4 + 6.3 + 9 = **59.7** | 2 警戒（レベル3の一歩手前） |
| 50 mm/h | 50/23.3 × 1.25 = 2.68→2.0 | 2 | 60 + 13 + 9 = **82** | 4 通行不能情報 |
| 80 mm/h | 上限 2.0 | 3 | 60 + 19 + 9 = **88** | 4 |

この地点は「**時間雨量30mm台後半で赤、50mmで黒**」という感度になる。
一方、ポンプ付き・平坦な地点（`T60 ≈ 60`）は50mm/hでもレベル1〜2に留まる。
**同じ雨でも地点で判定が分かれる**という、狙った挙動になっている。

## 7.5. 実データで判明した限界（2026-08-22）

千葉県内95箇所の実データを通したところ、**強い雨で判定が分かれない**ことが分かった。

| 時間雨量 | 判定の内訳（89件） |
|---------|------------------|
| 30 mm/h | 注意21 / 警戒68 |
| 50 mm/h | 警戒10 / 危険79 |
| **80 mm/h** | **危険89（全部）** |
| **100 mm/h** | **極めて危険89（全部）** |

原因は**入力データが地点を区別できていない**こと。

- 95件すべてが `underpass_gravity`（既定値35mm/h）。資料にポンプ設備の記載がない
- 閾値 `T60` の実際の幅は **21〜49 mm/h**（中央値33.7）と狭い
- 80mm/h はどの地点の閾値も大きく超えるため、`I_rain` が上限2で頭打ちになる

### 定数をいじって「分かれているように見せる」ことはしない

閾値の幅が狭いのはデータの制約であって、係数を調整して差を作っても
**実態に基づかない精度を装うだけ**になる。次の3つで解く。

1. **ポンプ設備の有無**（35 vs 55 mm/h）— 幅が一気に広がる。
   [docs/08](08_自治体連携_打診文案.md) のBで千葉国道事務所に照会中
2. **実際の冠水記録での較正** — 2026年8月の千葉豪雨で「どこが実際に冠水したか」を
   集め、それに合うよう閾値とレベル境界を決める（下の「検証方法」）
3. **`dz` の信頼性向上** — 標高データは地表を測るため、トンネル・ガード下では
   道路面ではなく上の地形の高さが出る。使える地点と使えない地点の区別が要る

### それまでの伝え方

**全地点が同じレベルになる状況では、「どの道が危ないか」ではなく
「どの道も危ない＝運転を控える」と伝える。** アプリでは、最高レベルの地点が
9割を超えたら専用の帯を出す（`prototype/index.html` の `updateExtremeBar`）。

あわせて、同じレベル内でもスコア順に並べた「危険な順」を出し、
レベルだけでは分からない差を補う。

## 8. 検証方法

1. **後ろ向き検証（backtest）**: 2026-08-13〜16の千葉豪雨の雨量データを流し込み、
   実際に冠水した箇所がレベル3以上になるか、しなかった箇所がレベル1以下に留まるかを確認する。
   評価指標は **再現率（見逃しの少なさ）を優先し、適合率は0.5以上を目標**（安全側に倒す方針より）。
2. **ROC/しきい値調整**: レベル境界の `S` は固定値ではなく、backtestで調整可能な設定値にする。
3. **地点別カルテ**: 各地点の `T60` と実績を並べたレビュー画面を作り、明らかに外れている地点を人手で補正できるようにする。
